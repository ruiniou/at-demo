# Atlas · Metadata Changes（思路2）完整流程 + Quote引用 Proposal

## ① 问题背景

此前的Proposal梳理了Metadata修改同步到代码的整体交互，并提出了两个呈现方向供决策（思路1：Diff展示在吸顶Dock卡片；思路2：Diff展示进Metadata面板本身，Track Changes呈现）。经过Demo反复验证，**思路2**在Component分组天然性、不受Dock尺寸限制等方面优势明显，成为进一步细化的方向。

在细化过程中，两件事需要补充定义：

1. **思路2的完整流程仍有缺口**：吸顶区域只保留一个改动数量的轻量提示，不再展示列表详情——但"详情去哪了"这件事没有交代清楚：发送出去的Prompt该携带什么内容？面板的"待更新"展示状态在用户点击发送之后应该怎么处理？这个问题此前一直悬而未决。
2. **新增引用（Quote）需求**：客户希望能快速把Metadata面板里的字段或Component引用进对话输入框，用于提问或指定改动意图，且一次输入里可能引用多个对象、每个对象各自搭配不同的说明——这要求引用内容能够穿插在文字中，而不是统一堆叠展示。

本Proposal的目的：把思路2的完整闭环定下来，并把Quote机制的交互规则一并定义清楚。

## ② 主要改进点

| 项目 | 定义 |
|---|---|
| Metadata面板两态 | **默认态**（正常编辑视图）与 **To be Updated态**（Track Changes展示：字段划线/新值标注、Tab角标、Component新增/删除呈现），点击Update Code后自动切入后者 |
| 吸顶Header | 仅显示图标+改动数量+×，不展示任何列表内容，详情完全交给Metadata面板承载 |
| 发送后的Prompt构成 | 用户输入的说明文字（含行内引用Tag，位置原样保留）+ 系统自动附加的完整分组Diff（字段级old→new，含新增/删除Component），后者不需要在界面上单独展示堆叠细节，但必须作为上下文一并发送，并保留在对话历史中可展开查看 |
| 面板态在发送后的处理 | 发送后面板**不立即**回到默认态，维持To be Updated展示，直到AI返回成功才切回默认（与Baseline只在成功时移动的既有规则保持一致） |
| Quote（引用） | 支持字段级与Component级两种粒度，点击Hover揭示的引用图标后，在输入框**当前光标位置**插入行内Tag，可以在多个引用之间穿插撰写不同说明 |
| 引用Tag的删除 | 点击Tag自带的×，或光标紧邻Tag时按退格整体删除（不拆成单字符） |
| 发送后的引用Tag | 在消息历史中保留展示，但隐藏×（历史记录不可再编辑） |

## ③ 设计方案

### Happy Path（完整版）

1. 用户编辑Metadata，净Diff > 0，Update Code按钮出现
2. 点击Update Code：
   - Metadata面板切入 **To be Updated态**：改动字段做Track Changes标注，Basic Info / Components两个Tab标题出现数量角标，新增Component带"New"标签，删除Component从列表移除并以说明文字呈现
   - Copilot吸顶Header仅显示"Metadata Changes · N"，不展开任何列表
3. 用户可以在Metadata面板任意字段或Component标题上，通过Hover揭示的引用图标，把它插入到输入框当前光标处（不论该字段是否属于本次Diff），并在多个引用之间穿插撰写各自的说明
4. 用户点击发送：
   - Metadata面板**维持**To be Updated展示（不因为发送就切回默认，见下方专门说明）
   - 实际发出的Prompt = 用户输入的文字（含行内引用Tag）+ 系统附加的完整分组Diff（字段级old→new）
   - 输入框进入生成中状态（已有方案，不在本次范围）
5. AI返回成功：
   - Baseline前移，Metadata面板此时才切回默认态
   - 对话流中出现历史消息：说明文字（引用Tag保留展示但隐藏×）+ 上方的Metadata Changes历史Tag，点击可展开查看完整分组Diff（复用已有的只读展示组件）
6. AI返回失败：面板本就还在To be Updated态，不需要额外处理（已有方案，不在本次范围）

### 面板"待更新"态在发送后如何处理（此前遗留的开放问题，本次定论）

结论：**沿用"Baseline只在同步成功时移动"这条已经确认的规则，面板的展示状态直接跟着这条规则走**——既然代码还没有真正更新完成，面板就不该提前表现得"好像已经处理完了"。所以：

- 发送这个动作本身，**不触发**面板从To be Updated切回默认
- 只有AI明确返回成功，Baseline真正前移，面板才切回默认态
- 失败的话，面板保持原样，不需要专门设计"失败态"的面板展示——它本来就还停留在To be Updated
- 生成中期间，字段依然可编辑（沿用"提交锁定，新编辑计入下一批"的既有规则），不需要为面板额外叠加一个"生成中"的专属视觉状态——生成中的提示已经由Copilot侧输入框承担，面板维持既有的To be Updated展示即可，不重复设计

这样处理的好处是：面板的视觉状态和Baseline的实际状态始终一致，不会出现"发送瞬间UI显示已经改完、但代码其实还没改完"这种误导性的中间态。

### Quote机制细节

- **触发方式**：Hover字段行或Component标题时露出引用图标（复用"Hover只揭示可操作图标"的既有原则），点击后插入
- **插入位置**：输入框当前光标处，不是堆叠在输入框上方——这样同一次输入里，用户可以对不同引用对象分别撰写说明，而不是所有引用共享同一段说明文字
- **Tag内容**：字段级引用显示为"组件名 · 字段名"（Basic Info下的字段显示为"Basic Info · 字段名"）；Component级引用显示为"组件名"
- **引用范围**：不限于本次Diff涉及的字段——不论字段是否有pending change，都可以被引用，因为引用的诉求可能是提问、也可能是指定改动意图，不应该被"是否在这次Diff里"限制住
- **删除方式**：点击Tag自带的×，或光标紧邻Tag时按退格，作为一个整体删除

## ④ MVP范围说明

本次聚焦以下内容：
- Metadata面板两态定义，及发送后面板状态的处理规则
- 发送Prompt的实际构成（说明文字+引用Tag+完整分组Diff）
- Quote的插入/删除交互规则

不包含以下内容：
- 生成中/失败态的具体样式（已有方案）
- 引用一个本身带pending diff的字段时，Tag要不要额外携带old→new值（见TBD）
- 多用户协作编辑同一Metadata导致的冲突场景

## ⑥ 附录：状态表

| 场景 | Meta Update按钮 | Metadata面板 | 吸顶Header | Diff / Baseline |
|---|---|---|---|---|
| 无变化 | 不显示 | 默认态 | 无 | diff = 0 |
| 有编辑，未点击Update | 显示，数量=净diff | 默认态（字段已改但未标注Track Changes） | 无 | diff > 0，Baseline不变 |
| 点击Update | 隐藏 | To be Updated态 | 仅数量Tag | 同上，Baseline不变 |
| 待更新期间继续编辑（含引用操作） | 仍隐藏 | 实时更新Track Changes标注 | 数量同步更新 | diff更新，Baseline不变 |
| 点击 ×（退出到默认） | 重新显示（diff仍在） | 切回默认态 | 消失 | diff/Baseline均不变 |
| 发送 | 禁用 | **维持To be Updated态**（不因发送切回） | 消失，转为对话流历史Tag | 本批锁定待处理，Baseline暂不变 |
| 生成中期间继续编辑 | 仍禁用 | 新编辑同步标注（不属于已锁定批次） | — | 新编辑独立累积，计入下一次diff |
| AI返回成功 | 按剩余diff重新判断显隐 | 切回默认态 | 对话流历史Tag可点击查看完整存档 | Baseline前移，Edited字段→Unconfirmed |
| AI返回失败 | 重新启用（diff仍在） | 维持To be Updated态（本就未切回） | 已有失败方案，不在本次范围 | Baseline不变，Diff完整保留 |
