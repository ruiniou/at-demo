# Atlas · Metadata Changes 流程改版 Proposal

## ① 问题背景

最初的问题是：Metadata修改同步到代码时，采用预填一整段Brief进Copilot输入框的方式，用户不清楚该补充什么、该从哪改起，尤其大多数改动本身并不需要说明。

在此基础上，设计经过了几轮收敛：

1. 引入 **To be Updated Card**（对话流内详情卡） + **Metadata Changes Chip**（吸顶摘要），把"展示改动"和"是否需要说明"拆开
2. 出于收敛决策路径、减少点击的考虑，把这套双重结构（对话流Card + 吸顶Chip）**合并成单体Dock**：取消对话流内的Card，只保留吸顶的 Metadata Changes Header（折叠/展开 + × 关闭），同时取消 Proceed / Cancel 两个二级按钮，提交动作直接复用输入框本身的发送
3. 由于Dock本身尺寸受限（约352px宽 / 展开态最高约400px），"Diff该怎么在这么小的空间里呈现"成为一个独立问题，衍生出两个方向

本Proposal的目的：把合并后的核心交互规则定下来（两个方向共用的部分），并把两个衍生方向的方案摆出来供决策，明确各自的适用前提和代价。

## ② 主要改进点

| 项目 | 定义 |
|---|---|
| 单体Dock | 取消对话流内Card，只保留吸顶Header，避免同一份信息出现在两个地方 |
| 取消Proceed/Cancel | 提交动作复用输入框发送（空内容=按AI理解处理，带说明=按说明处理）；× 图标承担原Cancel的"暂不处理"语义 |
| Update对象 | 净Diff：当前Metadata状态相对于Baseline的差异，按字段折叠 |
| Baseline | 仅在AI Copilot **同步成功**时前移，点击Update / 关闭Header（×）/ 提交失败均不移动 |
| 新增Component | 在Components列表中正常显示，带"New"标签，直到同步完成后消失 |
| 删除Component | 二次确认后直接从列表移除（沿用现有删除交互习惯），不做保留态展示 |
| 对话流历史记录 | 发送后，Dock内容收成消息上方的一个Tag，点击可展开只读、完整的当次Diff详情，作为可追溯的存档 |

## ③ 设计方案

### 共用基础（两个思路均适用）

**Happy Path**
1. 用户编辑Metadata，净Diff > 0 时，Meta面板的Update Code按钮出现
2. 点击Update Code：Copilot吸顶Header出现（折叠态：图标 + Metadata Changes + 数量 + ×）
3. 用户可继续编辑Metadata，Header数量与状态实时同步
4. 用户直接发送（不输入文字）或补充说明后发送 → 提交
5. 提交后：Header消失，输入框进入生成中状态（已有方案，不在本次范围）
6. 成功：Baseline前移，历史记录以消息上方Tag的形式留存
7. 失败：不在本次范围（已有方案）

**规则边界**
- 净Diff计算方式、Baseline定义、提交锁定期间新编辑不合并入当前请求等规则，均沿用此前已确认的定义，不因呈现方式改变而变化
- × 只影响是否默认Mention，不影响Diff/Baseline

---

### 思路1：Diff完整展示在吸顶Dock卡片内

点击chevron展开Header后，卡片内以"组"为单位列出本次改动，**不论改动条数多少，统一采用收起态优先的呈现方式**（不再区分≤5/>5两种模式，避免同一个组件在不同改动量下呈现规则不一致）：

- 每个改动所属的Component（含Basic Info，作为隐式分组）默认收起为单行摘要："组件名 · N处改动 ▸"，点击展开该组下的字段级Diff（旧值→新值）
- 若某个分组下只有1个字段发生变化，**不展示数量**，只显示"组件名 ▸"，避免出现多余的"1"造成视觉噪音
- **新增/删除的Component单独处理**：以独立单行呈现，不参与展开/收起（因为没有字段级细节可展开）——新增显示为"＋ 组件名（New）"，删除显示为"－ 组件名（Removed）"，图标颜色用中性色系，不用红色（避免和现有Conflict标签的语义冲突）
- 展开某个分组后，组内字段行采用"字段名"与"Diff值"上下堆叠的两行结构，Diff值**允许换行、不做截断**，避免长文本被压缩成省略号丢失信息

#### 折叠/展开与交互规则小结：

1. **Metadata Changes 吸顶 Dock 卡片**：
   - **单项改动**：当全局仅有 1 项 Metadata 改动时，自动直接展开该组件分组，并**隐藏组件层级的 Chevron 箭头**（避免视觉冗余）。
   - **多项改动**：多项改动一次性触发时，各组件分组默认收起折叠。
   - **追加改动**：若用户在 Metadata Changes 已打开状态下继续在面板追加改动，已有分组保持原状态，**新出现的组件分组自动直接展开**。

2. **对话流 Prompt 气泡历史 Tag (`Metadata changes Tag`)**：
   - **单项改动**：仅 1 项改动时，Tag 默认直接展开；多项改动时，Tag 默认收起折叠。
   - **只读快照**：Tag 属于历史提交快照，展开后内容**仅供查看、不可交互**（移除点击跳转/Focus 绑定）。

**优点**：用户全程停留在Copilot侧就能完成审阅和发送，不需要切换视线到Metadata面板

**局限**：受限于Dock的固定尺寸，字段值较长或改动较多时，即使有折叠机制，仍然是"信息被压缩进一个小容器"的体验；Component分组关系需要在这个卡片里单独维护一套展示规则

---

### 思路2：Diff展示进Metadata面板本身（Track Changes模式）

点击Update Code后，**Metadata面板整体切换进"待更新"模式**：各字段以Track Changes的方式标注（旧值划线，新值以强调色+下划线呈现，字段左侧加色条标记"这是改动过的字段"），Components列表中新增的Component带"New"标签；Basic Info / Components 两个Tab标题上加数量角标，提示"该Tab内还有N处改动"，避免改动分散在不同Tab时被漏看。

吸顶Header在此思路下**大幅简化**：只显示一个轻量Tag（图标+数量+×），**不展开任何列表**——因为Diff详情已经在Metadata面板里完整呈现，不需要在Dock里重复一份。

Metadata面板因此有两个模式：
- **默认模式**：正常编辑视图
- **待更新模式**：Track Changes展示视图，点击Update Code后自动进入

用户可以主动**退出**待更新模式，回到默认视图——这个"退出"和吸顶的×是同一个语义（暂不处理，不影响Diff/Baseline，只是不再突出显示）。用户发送后，面板的待更新标注消失、Header的Tag清空，本次改动记录转移到对话流消息上方的Tag里存档。

**优点**：不受Dock尺寸限制，Diff展示空间等于Metadata面板本身的可用空间；Component分组是面板的原生结构，不需要另外设计一套分组呈现规则；改动发生的位置和展示的位置是同一个地方，认知负担更低

**局限**：依赖Metadata面板与Copilot面板并排同时可见的布局（已确认符合你们当前的典型布局，但如果未来布局调整为互斥展示，这个前提会失效）；涉及Metadata面板本身新增一套展示模式，改动范围比思路1更大，需要面板侧的工程改动，不只是Copilot组件内部的事

---

### 两个思路的关键差异对比

| 维度 | 思路1（Dock内展示） | 思路2（面板内Track Changes） |
|---|---|---|
| Diff呈现位置 | 吸顶Dock卡片 | Metadata面板 |
| 吸顶区域内容 | 完整字段清单（可折叠） | 仅一个数量Tag，无列表 |
| 空间约束应对 | 依赖折叠/收起规则缓解 | 天然不受352×400限制 |
| Component分组 | 需要单独设计分组/收起规则 | 面板原生结构自带，无需额外设计 |
| 依赖前提 | 无特别前提 | 依赖两面板并排可见 |
| 用户视线路径 | 全程停留在Copilot侧 | 需要在Metadata和Copilot之间来回扫视 |
| 工程改动范围 | 主要在Copilot组件内 | 涉及Metadata面板新增展示模式，改动面更大 |

## ④ MVP范围说明

无论最终选择哪个思路，以下是两者共用、且已经确认可以先行推进的基础部分：

- 单体Dock结构（取消对话流Card，取消Proceed/Cancel）
- 净Diff / Baseline的计算与状态机规则
- 新增/删除Component的呈现规则
- 对话流历史Tag（发送后收起为Tag，点击展开只读完整Diff）

**思路1和思路2具体选哪个，作为本次的核心待决策项**，不在MVP范围内直接定论（见TBD）。

不包含以下内容：
- 生成中/失败态的具体呈现（已有方案）
- 多用户协作编辑同一Metadata导致的冲突场景

## ⑥ 附录：共用状态表

| 场景 | Meta Update按钮 | 吸顶Header/Tag | Diff / Baseline |
|---|---|---|---|
| 无变化 | 不显示 | 无 | diff = 0 |
| 有编辑，未点击Update | 显示，数量=净diff | 无 | diff > 0，Baseline不变 |
| 点击Update | 隐藏 | 出现（思路1：展开详情列表；思路2：仅Tag，面板进入待更新模式） | 同上，Baseline不变 |
| 停留期间继续编辑 | 仍隐藏 | 数量/内容实时更新 | diff更新，Baseline不变 |
| 点击 ×（或思路2的"退出"） | 重新显示（diff仍在） | 消失/面板回默认模式 | diff/Baseline均不变 |
| 发送（提交） | 禁用 | 消失，转为对话流Tag | 本批锁定待处理，Baseline暂不变 |
| AI返回成功 | 按剩余diff重新判断显隐 | 对话流Tag可点击查看完整存档 | Baseline前移，Edited字段→Unconfirmed |
| AI返回失败 | 重新启用（diff仍在） | 已有失败方案，不在本次范围 | Baseline不变，Diff完整保留 |
