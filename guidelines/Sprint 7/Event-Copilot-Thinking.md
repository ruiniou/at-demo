# event-copilot-thinking-retry-proposal

# Event Copilot — 过程可见性与执行异常处理 Proposal

**模块**：Event Copilot（跨表任务编排层）
**范围**：本提案仅覆盖以下三项，均为本轮讨论中已收敛的结论：

1. Thinking（过程可见性）能力，可折叠
2. Retry 的适用范围区分（Blocked 可重试 / Failed 不可重试）
3. Blocked、执行失败等结果状态在界面上的呈现规则

---

## 一、背景

Event Copilot 目前的对话呈现是单一形态：无论是在陈述筛表结论、执行状态还是异常情况，都用同一种 Markdown 文本气泡承载。这带来两个问题：

- **筛表结论的可信度无法核实**：确认卡上的”命中原因”是 AI 生成的一句话摘要，用户没有渠道看到这句话背后经过了哪些检索、判断步骤，只能选择相信或不相信。
- **执行失败被当作同一种结果处理**：目前所有未成功的情况都归为”需处理”，但实际上”批次间排队冲突”和”AI 判断代码无法安全修改”是两种性质完全不同的失败——前者是资源竞争，等一等或重试就可能解决；后者是确定性的技术障碍，重试没有意义。不作区分会让用户对着不该重试的失败反复点击，或者对该重试的失败误以为要手动介入。

## 二、Thinking（过程可见性），可折叠

### 2.1 目的

让”命中 N 张表”这个结论有过程支撑，用户不需要逐张表去肉眼核实 AI 的筛选依据，想审计时可以展开查看，不想看时不打扰对话节奏。

这个模式并非新造——Atlas 现有单表 Copilot 界面上已经有”Complete thinking”这一折叠项的先例，本提案是把同一套设计语言在 Event Copilot 的跨表场景里延伸使用。

### 2.2 内容构成

Thinking 块内呈现三类过程，对应 Event Copilot 实际会做的判断工作：

| 步骤 | 内容示例 |
| --- | --- |
| 🔍 检索 | 按精确属性 → 变量匹配 → 关键词模糊匹配的顺序，扫描全部候选表的 Metadata 与代码 |
| 🧠 分析 | 对模糊匹配的表说明判断依据（例如：命中关键词但语境存疑，因此标记为”疑似”而非直接排除或命中） |
| 🔗 依赖检查 | 检查本次修改涉及的变量/Macro 是否被其他未直接命中的表间接引用 |

### 2.3 交互规则

- **运行时**：可以参考常见IDE的UI交互，Thinking 块默认展开，有最大高度，上下可以用像AI copilot顶部栏下方的渐变阴影一样做遮罩。Thinking过程用Markdown text。但搜索需要Icon+Searched XX TFL或者XX对象展示
- **完成后**：自动折叠为一行摘要（例如Icon+Searched N TFLs可折叠），不占用对话空间。
- **可复查**：折叠后仍可随时点击展开，重新查看具体内容——这是审计需求，不是一次性的加载动画。
- **位置**：出现在 Event Copilot 对话流中，紧跟在用户需求描述之后、AI 给出筛表结论/确认卡之前，作为两者之间的过程记录。
- 当Scope卡片被用户批准执行：Scope卡片自动折叠。

## 三、Retry 的适用范围区分

### 3.1 两种失败的性质定义

| 类型 | 成因 | 是否可恢复 | 对应操作 |
| --- | --- | --- | --- |
| **Blocked（排队冲突）** | 该表在执行阶段被另一个正在跑的 Event 批次占用 | 是——占用方任务结束后锁会释放 | 提供 **Retry** |
| **Failed（执行失败）** | AI 判断代码结构无法安全自动修改（如变量写在自定义 Macro 参数中） | 否——问题出在代码本身，不会因为再跑一次而改变 | 无 |

区分依据是”再试一次是否可能有不同结果”，而不是”是否需要用户介入”——两者都需要用户知道，但只有前者值得让用户多点一次按钮。

这里需要你考虑下用哪种：Warning/Danger/Alert

### 3.2 Retry 的具体行为

1. 点击 Retry 后，**重新检查该表当前的锁状态**，不假设占用一定已解除；若仍被占用，回到”排队中”的展示，不给用户一个虚假的”已解决”信号。
2. 重试成功后的结果**归属于同一批次**（例如 EVT-0917-01），不生成新批次——这是同一次任务的收尾动作，不是一次新请求。
3. Retry 按钮只出现在 Blocked 状态的行上

## 四、Blocked / 执行失败等结果状态的呈现规则

### 4.1 状态分类与视觉语言

| 状态 | 说明 |
| --- | --- |
| 已更新 | 成功执行 |
| 🔒 排队冲突（Blocked） | 被另一批次占用，可重试 |
| ❌ 执行失败（Failed） | AI 确定无法安全执行，不可重试 |

### 4.2 信息密度原则：Event 侧低密度，TFL 侧高密度

- **汇总卡（Event 侧）**：每行只保留”状态 Badge + 表名 + （视情况）Retry”，不展示任何代码或详细原因文本。Event Copilot 的职责是让用户知道”有哪些表、状态如何”。
- 边界情况：过程中的卡片（Scope，进度和汇总）可能都需要一个最大高度，万一命中TFL是10个以上，会导致对话流高度都被卡片占满。
