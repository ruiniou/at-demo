# PRD：Event 级 AI Copilot

## 1. 背景

当前 Copilot 主要在单个 TFL（表）内工作：生成代码、回答问题、根据用户反馈修改表。

但实际工作中，许多需求会同时影响一个 Event 下的多张表，例如变量替换、Macro 更新、数据更新后的重检、相似表同步修改。

Event 级 AI Copilot 是面向整个Event的跨表协作助手。它负责理解用户的 Event 级需求、识别可能受影响的 TFL、展示建议范围、在用户确认后派发任务，并汇总执行结果。它不直接替代单表 TFL Copilot 的代码处理能力。

---

## 2. 产品目标

### 2.1 核心目标

让用户能够在 Event 范围内：

- 发起跨表修改或影响分析；
- 清楚知道哪些表会被影响、为什么被选中；
- 在执行前确认或调整修改范围；
- 跟踪批量任务的排队、执行和结果；
- 下钻到单表查看具体修改过程；
- 从单表修改扩展到相似或相关表。

### 2.2 非目标

- Event Copilot 不直接替代单表 Copilot 编写或修改代码。
- 不承诺一次性自动识别所有复杂、隐式依赖。
- 表分类、相似表参考等能力可作为后续增强，首版不应依赖其准确性。

---

## 3. 用户与核心场景

1. 用户发起跨表修改
•	例如：替换变量、更新 Macro、统一格式或统计口径。
•	用户在 Event 层提出意图，系统筛选相关 TFL，用户确认后批量执行。
2. 数据更新后的影响处理
•	Shell 更新时，直接向关联 TFL 下发更新任务。
•	Item 或其他数据更新时，先识别变化及潜在波及变量，再筛选受影响 TFL。
3. 从单表修改扩散到相似表
•	用户在某一 TFL 完成修改后，选择将修改意图交给 Event Copilot。
•	Event Copilot 识别可能适用的其他 TFL，供用户确认后执行。
4. 跟踪批量任务
•	用户查看命中 TFL、排队、执行、完成、失败或需人工处理等状态。
•	用户可从 Event 任务下钻到具体 TFL 的处理结果。

---

## 4. 核心概念

| 维度 | Event Copilot | TFL / 单表 Copilot |
| --- | --- | --- |
| 工作范围 | 整个 Event、多个表 | 一张表及其会话 |
| 主要角色 | 理解任务、找表、确认范围、调度、汇总 | 理解本表上下文、决定是否改、生成或修改代码 |
| 是否直接改代码 | 原则上不直接改 | 是 |
| 上下文 | Event 状态、表目录、筛选结果、任务进度 | 本表数据、代码、历史对话与生成过程 |

### 4.1 Event

一个 Event 对应一个任务范围，包含原始输入、多个 TFL、全局状态和若干 Event Session。

### 4.2 TFL

TFL 是 Event 下的单张表。每张表有自己的状态、代码、数据上下文和多个对话 Session。

### 4.3 Event Copilot

跨表的上层 Agent。负责：

- 理解 Event 级用户需求；
- 找出候选 TFL；
- 解释命中原因；
- 获取用户确认；
- 派发变更意图；
- 汇总执行结果。

### 4.4 TFL Copilot

单表执行 Agent。负责：

- 基于该表的数据、代码与对话历史理解任务；
- 判断是否需要修改；
- 决定如何修改；
- 执行、失败或拒绝后回传结果。

### 4.5 Session

| 类型 | 定义 | 核心内容 |
| --- | --- | --- |
| Event Session | 用户与 Event Copilot 的一次 Event 范围对话/任务上下文 | 需求、筛表、确认、派发进度、汇总 |
| TFL Session | 用户或 Event 任务与某张表 Copilot 的一次表级对话/执行上下文 | 表内推理、代码、修改记录、结果 |

同一 Event 和同一 TFL 都可存在多个 Session；TFL 还需要标记当前有效或最新版本，用于后续继续编辑和任务派发。

## 5. 功能需求

## 5.1 Event Session 与对话分岔

### 功能说明

用户可在同一 Event 下创建多个 Event Session，用于处理不同的跨表议题。

支持：

- 新建 Event Session；
- 查看历史 Event Session；
- 从历史消息节点修改或分岔；
- 从默认节点新开 Session；
- 保留原始对话路径，不覆盖历史结论。

### 交互规则

- 用户点击“新建对话”时，默认可从代码生成完成后的节点开始，不继承后续对话。
- 用户从某条历史消息选择“修改”或“分岔”时，新 Session 从该消息开始。
- 分岔需展示来源 Session 和来源消息，帮助用户理解上下文。

---

## 5.2 跨表请求与意图理解

### 支持场景

1. **用户直接批量修改**
    - “把使用 A 的表改为 B”
    - “统一调整某类表的格式”
    - “将某个 Macro 替换为新方式”
2. **数据 Diff 触发**
    - Item 或数据更新后，判断受影响的表；
    - 前置模块产出数据变化及可能波及的变量，再由 Event Copilot 筛表。
3. **Shell 变更触发**
    - Shell 更新时，不需要再用三层搜索去找受影响的表，可直接根据 Shell 与表的关联关系定位关联表并派发任务；
    - 派发后仍由各表 Copilot 基于自身上下文判断是否需要修改、如何修改；
    - 各表 Copilot 在执行修改时读取最新 Item；
    - 前提：系统能可靠维护并检索 Shell → 关联表 / 关联对话的映射（见 TBD-03）。
4. **单表修改扩散**
    - 用户在 TFL 内完成修改；
    - TFL Copilot 总结修改意图；
    - 用户选择扩散后，进入 Event Copilot 做范围识别与确认。

---

## 5.3 筛表与影响范围确认

### 筛表逻辑

系统按以下优先级筛选：

1. 表名、编号、类型、字段等精确属性；
2. 变量、Macro 等 Agent State 信息；
3. 代码、JSON 或关键词模糊匹配；
4. 必要时全局扫描。

全局扫描成本高，应作为兜底能力，而非默认路径。若无法形成搜索条件，系统可先返回 Event 内所有表的简介，供 Copilot 判断。

### 确认页要求

执行前必须展示：

- 命中 TFL 数量；
- 每张表名称与状态；
- 每张表的命中原因；
- 预计操作类型；
- 可能的风险或无法判断项；
- 被锁定、未完成或没有代码的表。

用户可：

- 确认全部；
- 取消勾选部分表；
- 补充条件；
- 回到对话继续收敛范围；
- 取消任务。

---

## 5.4 派发与单表执行

### 执行原则

Event Copilot 只向 TFL Copilot 派发：

- 用户目标；
- 数据变化线索；
- 命中原因；
- 关联证据；
- 来源 Event Session。

不派发具体代码修改方案。具体是否修改、如何修改，应由 TFL Copilot 根据本表历史上下文、已有代码和最新数据决定。

修改的作用对象（Code / Metadata / 两者）尚未确认，见 TBD-01。

### 结果状态

每张 TFL 至少应回传：

- 已更新；
- 无需更新；
- 等待中；
- 执行中；
- 失败；
- 需要用户处理；
- 已跳过；
- 被锁定。

Event 级任务汇总这些结果，并支持下钻查看单表详情。

---

## 5.5 队列、进度与锁定

### 队列

跨表任务可能同时涉及大量 TFL，受共享并发限制影响，部分表会进入等待队列。产品需展示：

- 总表数；
- 排队中数量；
- 执行中数量；
- 已完成数量；
- 失败或需处理数量；
- 当前进度；
- 单表状态变化。

用户自带 API Key 的并发能力可能较低，讨论中预期约为每 Key 7–8 个并发；后续可能增加 per-reporting-event 隔离队列。

### 锁定

建议在 TFL 被 Event 任务处理时加锁：

- 被锁表不接受用户或其他 Copilot 的新指令；
- 第二个请求直接提示“该表正在被任务处理”，不自动排队；
- 任务结束、失败或取消后释放锁；
- 锁定状态应在 Event 列表和单表页都可见。

TFL 的访问与接管机制（先到先得：无人访问时进入者自动成为 Owner，Owner 在线时后来者仅可查看）无法覆盖 Event 批量派发场景，两者如何共存见 TBD-02。

---

## 5.6 版本、重试与当前 Session

同一 TFL 可能有多次生成、重试、分岔或来自 Event 的派发任务。产品需要：

- 标识每个 TFL Session 的来源：
    - Batch 生成；
    - 用户直接操作；
    - Event Copilot 派发；
    - 从其他会话复刻/分岔；
- 标记“当前有效版本”；
- 支持查看历史版本，但避免用户误在过期 Session 上继续操作；
- 在 Event Copilot 派发时默认使用该 TFL 的当前有效版本。

---

## 5.7 表分类与相似表能力（后续增强）

### 目标

为表建立可解释的相似性线索，例如：

- 统计方法；
- Population 类型；
- Macro 使用情况；
- 表结构或字段；
- 生成逻辑。

### 可支持的能力

- 筛表时将分类作为辅助条件；
- 单表更新后推荐相关表；
- 首次生成时，为相似表提供参考表；
- 让用户在批量任务中按类别确认表范围。

### 限制

AI 初步分类可作为线索，但不应自动视为确定关系；可引入 Programmer 的确认或修正流程。

## 6. 关键用户流程

### 6.1 用户发起跨表修改

1. 用户进入 Event，创建或进入 Event Session。
2. 输入跨表需求。
3. Event Copilot 解释理解到的意图并开始筛表。
4. 系统返回候选表、命中原因和风险。
5. 用户确认、排除或补充条件。
6. 系统锁定相关表并开始派发。
7. 用户在任务面板查看队列和执行状态。
8. 系统返回整体汇总。
9. 用户可进入任意 TFL 查看细节或继续对话。

### 6.2 数据更新触发影响检查

1. Event 数据更新。
2. 前置模块识别变化项与潜在波及变量。
3. Event Copilot 创建或提示一个影响检查任务。
4. 系统筛表并展示影响范围。
5. 用户确认后下发更新任务。
6. 汇总结果。

### 6.3 从单表修改扩散

1. 用户在 TFL Copilot 完成一项修改。
2. 用户点击“应用到相关表”。
3. TFL Copilot 总结变更意图，转交 Event Copilot。
4. Event Copilot 搜索可能适用的表。
5. 用户确认范围。
6. 批量派发并汇总。

## 7. 状态模型

### Event 状态

- 空
- 待确认
- 排队中
- 执行中
- 部分完成
- 已完成
- 失败
- 已取消

已取消的 Event 不可继续执行；如需继续，应重新创建。

### TFL 任务状态（前台展示）

- 待确认
- 排队中
- 执行中
- 已锁定
- 已更新
- 无需更新
- 已跳过
- 失败
- 需人工处理

### TFL 内容状态（后台标记）

仅作为系统内部标记，用于判断该表是否可被派发，不作为前台独立状态展示。

- 未生成
- 无代码
- 可执行

## 8. UX 设计原则

1. **先范围、后执行**
    
    跨表改动必须先展示影响范围并要求确认。
    
2. **全局调度与局部执行分离**
    
    Event 负责“找什么、改哪些”；TFL 负责“本表如何改”。
    
3. **上下文可追溯**
    
    用户能追踪 Event Session、TFL Session、派发来源、版本关系和任务结果。
    
4. **进度可见**
    
    不能只展示统一 loading；需清晰表达排队、执行、完成、失败与锁定。
    
5. **自动化可控**
    
    模糊匹配、相似表推荐和全局扫描应明确标示不确定性，保留用户确认。
    
6. **不要隐藏异常**
    
    失败、锁定、未生成代码、无法判断影响等都应显式呈现。

| TBD-07 | Event Session 是否需要支持分叉（从历史消息修改/分支）？

产品侧因为、可能带来的复杂度（已与 Architect 确认）：
1. 归属问题：批次固定归属于其发起时的原分支，新分支继承分叉点之前的会话记忆，包含批次的完整记录（改了哪些表、原因、结果），非仅“表已被改”这一事实。因此无论分叉多少次，查该批次本身即可追溶源头，不依赖梳理分支树。
2. 双层分叉树交叉问题：单表侧只允许存在一个生效会话，Event 派发任务与其他用户都受锁约束、不准同时发指令，因此一张表的修改永远只挂在一条执行链路上，不会真正同时归属于两个分叉。
3. 对用户的影响：用户需要同时维护两套分叉心智模型（Event 层一套，单表层一套）仍然成立，仍需 UI 展示优化（如将“继承来的批次”标记为只读历史，并可追溶回原分支）。

基于以上确认，Event 侧允许分叉。前提：批次对象（TBD-06）必须永久记录自己的发源分支/消息，并在任何继承它的分支中可被完整查看（非仅事实标记）。 | Event 侧允许分叉（已与 Architect 确认）；批次归属原分支，新分支可完整查看继承到的批次记录；单表侧单会话+锁机制避免实际执行冲突 | PM / Design | ✅ |
| TBD-08 | 筛表所依赖的变量、Macro 等 Agent State 信息具体从哪里来（User Input？ Metadata？两者同步关系是什么），谁维护、何时刷新 | 来自 User Input 或 Metadata | AI Architect / Backend | 🟡 |
| TBD-09 | 批量任务是否需要一个总览页，支持用户对整批表统一控制是否允许编辑/暂停（而非仅逐表查看锁定状态） | 需要，作为 5.5 任务面板的一部分 | PM / Design | 🟡 |
| TBD-10 | 前端入口是否将 Event 与单表合并为一个输入框（靠 scope 开关切换），还是拆为两个独立面板（Event 总览/Plan 面板 + 单表执行面板）？

此决定不能单独定，会反过来约束 TBD-07（分叉）和 TBD-02（锁定/权限）：

1. 与分叉的耦合：合并入口下，用户从历史消息发起分叉时，系统需先判断那条消息当时的 scope 是 Event 还是某张 TFL，才能知道分叉到哪个 Session；拆分为两个面板则分叉天然只发生在各自面板内，无需归属判定。
2. 与权限/锁定的耦合：合并入口下，用户将 scope 切换到一张已被其他人锁定/占用的 TFL 时，这个切换本身应该被拦截、还是允许仅只读进入，现无规则；拆分为两个面板则用户是通过“打开那张表”进入 TFL 面板，可在进入时自然展示“已锁定，只读”提示，与 5.5 现有锁定可见性设计一致。

即：入口越“合”，分叉与权限需补的规则越多；入口越“拆”，这两个问题越接近自约。三个 TBD 建议一并确认，不单独先定其中一个。
