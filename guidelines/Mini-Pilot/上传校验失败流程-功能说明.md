# 功能说明：上传校验失败流程（Upload Card 改造 + Import Errors Modal）

> 面向对象：AI编码工具（基于现有设计系统实现，需引用已有 Design Tokens / 组件规范，不要新建视觉样式）
> 所属产品：Atlas
> 涉及范围：Shell / ADAM 文件上传校验失败态

---

## 1. 背景

用户上传 Shell / ADAM 文件后，后端会返回结构化校验结果。当校验不通过时，当前设计直接在上传卡片内展示报错原文，存在以下问题：

- 报错条目多时，卡片内容无限增高，破坏页面布局
- 报错的结构化信息（类型/位置/详情）被压缩成一段文字，用户难以快速定位
- 卡片本身不适合承载"排查"这类需要持续阅读的任务

本次改造范围：
1. 改造「上传失败态卡片」，卡片本身只承担状态提示 + 摘要，不展示报错原文
2. 新增「Import Errors Modal」，承载完整的错误列表与排查交互

---

## 2. 后端数据结构（已确认）

后端校验规则以类型（type）为单位定义，每类规则对应一个固定的提示文案。校验结果为一个错误数组，每条包含：

```json
{
  "type": "Data Duplication",
  "message": "Duplicate Table No \"T-14.2.1\" found — this value already exists in Sheet 3, B5.",
  "sheet": "Sheet 4",
  "row": 2,
  "column": "A"
}
```

字段说明：

| 字段 | 说明 | 是否必现 |
|---|---|---|
| `type` | 规则类型，有限枚举（如 Data Duplication / Header Format Error / Missing Required Field） | 是 |
| `message` | 该类型规则对应的提示文案，原文展示，**不做截断** | 是 |
| `sheet` | 所在 Sheet 名称 | 否，全局性错误可能为空 |
| `row` | 所在行号 | 否，全局性错误可能为空 |
| `column` | 所在列 | 否，全局性错误可能为空 |

> ⚠️ `sheet` / `row` / `column` 三者要么同时存在，要么同时为空（代表全局性错误，非定位到具体单元格）。实现时按"整体缺失"判断，不要出现只缺一个字段的展示逻辑。

### 位置信息展示格式

`row` + `column` 需合并为标准单元格引用（Cell Reference）格式，即「列字母 + 行号」直接拼接，不额外加「Row」「Column」等词、不加分隔符：

```
row: 5, column: "B"  →  B5
row: 2, column: "A"  →  A2
```

`sheet` 与单元格引用之间用逗号连接（非圆点 `·`）：

```
Sheet 3, B5
Sheet 4, A2
```

单元格引用部分（如 `B5`）使用等宽字体展示，视觉上区别于 Sheet 名称的常规文本样式。全局性错误（三字段均为空）不展示这一行。

## 3. 组件一：Upload Card（失败态）

### 3.1 状态定义

Upload Card 在校验失败后进入 `failed` 状态，仅有一种展示结构，**不区分错误数量 = 1 与错误数量 > 1 两种情况**（这是对旧设计的修正，旧版本中"单条直接展示原文"的分支已废弃）。

### 3.2 卡片内容（业务逻辑，非视觉稿）

失败态卡片需展示：
- 状态标识：`Upload Failed`
- 摘要文案，格式为「错误数量 + 固定指示语」：
  - 错误数 = 1 时：`1 error found. Fix the error in the file and reupload again.`
  - 错误数 > 1 时：`{N} errors found. Fix errors in the file and reupload again.`
- 一个「View Details」入口，点击后打开 Import Errors Modal
- 一个「Re-Upload」操作按钮（沿用现有上传组件行为，不在本次改造范围内）

卡片**不展示** `type` / `message` / 位置信息，这些信息统一收敛到 Modal。

### 3.3 视觉实现要求

- 复用现有失败态卡片的容器样式（背景色、图标、Re-Upload 按钮样式均沿用设计系统已有 token，不新建）
- 卡片高度应为固定/可预期的，不随错误数量变化

## 4. 组件二：Import Errors Modal（新增）

### 4.1 定位与形态

- **标准 Modal**（非浮动窗口模式），带 backdrop，打开期间背景内容不可操作
- 使用场景：本 Modal 会嵌套在「Create New Event」这个父级 Modal 内部打开（各上传字段的「View Details」触发），属于 **Modal 套 Modal** 的场景。实现时需遵守以下边界规则：
  - **嵌套深度上限为 2 层**：Import Errors Modal 内部不允许再弹出任何第三层 Modal/浮层
  - **backdrop 做层级区分，而非独立叠加**：Import Errors 的 backdrop 透明度应比 Create New Event 的 backdrop 更深一档，视觉上体现"进入了更深一层"，而不是两层背景色简单相加变得过暗
  - 每个上传字段（ADaM Spec / SDTM / Shell file / TiFo）各自独立触发、独立管理自己的错误内容，互不影响（沿用各字段卡片已有的独立失败态管理逻辑，不需要额外处理）
- 标题固定为 `Import Errors`，**不展示文件名或其他动态副标题**
- 由 Upload Card 的「View Details」触发打开，点击关闭按钮或该次上传状态被新的上传行为覆盖时关闭

### 4.2 结构

Modal 从上到下分为四个区域：

1. **Header**：标题 `Import Errors` + 关闭按钮
2. **Toolbar**：左侧错误总数（`{N} errors found`），右侧视图切换控件（分段控件，两个选项：`By Position` / `By Type`，默认 `By Position`）
3. **Body**：错误列表，随所选视图切换展示逻辑（见 4.3）
4. **Footer**：固定展示「Re-Upload」按钮，操作后行为与卡片内 Re-Upload 一致

### 4.3 两种视图的业务逻辑

**By Position（默认视图）**

- 展示所有错误的平铺列表，顺序 = 后端返回顺序（即按 Sheet / Row 物理顺序）
- 每条错误为两列布局：
  - 左列：`type` 标签 + 位置信息（格式见「2. 位置信息展示格式」，三者若均为空则不展示这一行，仅保留 type 标签）
  - 右列：`message` 原文，不截断
- 列表顶部展示列头：`Location` / `Details`

**By Type（分组视图）**

- 按 `type` 分组，组内顺序 = 后端返回顺序
- 每个分组展示：
  - 分组标题：`type` 名称 + 该类型错误计数
  - 分组标题不可折叠，全部平铺，靠垂直滚动浏览
  - 组内每条错误为两列布局：
    - 左列：仅位置信息（不再重复展示 type 标签，因为分组标题已代表类型）
    - 右列：`message` 原文
  - 每个分组下方展示列头：`Location` / `Details`

**视图切换行为**

- 切换视图时，列表滚动位置重置到顶部（不做"保持当前错误在视野内"的定位逻辑）
- 切换视图不影响错误总数展示（Toolbar 计数与视图无关，始终显示全部错误数）

### 4.4 排序与滚动

- 无论哪种视图，均不做分页，错误条数多时使用容器内垂直滚动
- `message` 原文不做任何截断处理，无论长度

### 4.5 视觉实现要求

- 复用设计系统已有的浮动面板 / 分段控件（Segmented Control）组件规范，不新建样式
- `type` 标签使用与"错误/失败"状态色**不同**的强调色（避免和 Upload Failed 的红色状态混淆），具体取值引用设计系统已有的 tag/label token
- 列布局使用两列结构（左列定宽，右列自适应），避免因 `message` 不截断导致的长文本换行破坏对齐

---

## 5. 语言

本次改造涉及界面为**全英文**，不出现中文文案。所有本文档中出现的英文文案（如 `Upload Failed`、`{N} errors found. Fix errors in the file and reupload again.`、`Import Errors`、`By Position`、`By Type`、`Location`、`Details`）为定稿文案，AI 实现时直接使用，不做本地化处理。

## 7. 本次不做（Out of Scope）

- 报错定位跳转到用户原始文件的具体单元格（需要文件预览能力，非本次范围）
- 报错自动修复建议
- 按 type 筛选/隐藏功能（当前仅做分组展示，不做筛选交互）
- Re-Upload 按钮本身的上传逻辑（沿用现有组件，不在本次改造范围）
