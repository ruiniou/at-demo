# eTMF归档合规约束详解

> 设计iCTA拍照归档流程时的硬边界参考

---

## 核心合规框架

### GCP（ICH E6）对TMF的要求
- 所有文件必须**及时**归档（Contemporaneous）
- 文件必须保持**原始性**（Original），修改需留记录
- 文件必须在整个试验期间和结束后一定年限内**可获取**
- 必须有**清晰的文件分类体系**（通常对应TMF Reference Model）

### 21 CFR Part 11（电子记录要求）
| 要求 | 设计影响 |
|------|---------|
| Audit Trail（稽查轨迹） | 每个操作（上传/修改/删除）必须记录：谁、什么时间、做了什么 |
| 不可篡改性 | 文件一旦归档，不能直接覆盖，只能新建版本或走作废流程 |
| 访问控制 | 基于角色的权限，且要记录每次访问 |
| 电子签名 | 某些文件类型需要电子签名，签名需绑定个人身份 |
| 系统验证 | 系统需经过验证（Validation），设计变更需要评估验证影响 |

### ALCOA+ 在UI层面的体现
| 原则 | UI/UX体现 |
|------|---------|
| Attributable（可溯源） | 操作人信息自动记录，不允许匿名操作 |
| Legible（清晰） | 文件内容可清晰查看，图片质量要求 |
| Contemporaneous（及时） | 上传时间戳由系统生成，不允许用户修改 |
| Original（原始） | 拍照文件不得经过本地编辑再上传 |
| Accurate（准确） | 文件属性填写的验证规则 |
| Complete（完整） | 必填字段检查，不允许空缺提交 |

## iCTA移动端拍照归档已知约束

### 🔴 硬约束（不可违背）

1. **不留存本地**
   - 拍照后图片不得保存到设备相册/本地存储
   - 需要在系统层面限制（不是依赖用户自觉）
   - *设计含义*：拍照流程必须在App内闭环完成，不能调用系统相机后返回

2. **时间戳不可篡改**
   - 上传时间戳由服务端生成
   - 不允许用户指定"文件日期"（除非是文件本身记录的日期，与上传时间分开记录）

3. **操作可追溯**
   - 每步操作（拍照/上传/归档/QC通过/退回）都需要记录到audit trail

4. **文件不可直接覆盖**
   - 已归档文件有错误时，走"废止+新版本"流程，不能直接替换

### 🟡 通常约束（需和PM确认是否适用于太美实现）

5. **权限隔离**
   - 不同角色（CRA/CRC/研究者）可能有不同的归档权限
   - 某些文件类型可能只有特定角色能归档

6. **文件质量检查（QC）**
   - 上传前/后可能有自动或人工QC
   - 需确认QC不通过时的文件状态和后续流程

7. **查重机制**
   - 防止同一文件重复归档
   - 查重规则需确认（文件名？内容哈希？元数据组合？）

8. **必填元数据**
   - 归档时至少需要：文件类型（按TMF Reference Model）、关联的试验/Site/受试者
   - 具体字段需确认太美的实现

## 常见设计陷阱

### ❌ 陷阱1：让用户"先拍照后填信息"但没有容错
**问题：** 用户拍了10张照片后App崩溃，照片丢失
**解决：** 拍照后立即上传到临时区域，填完信息再归档；或分步保存状态

### ❌ 陷阱2：QC反馈不清晰
**问题：** QC不通过只提示"上传失败"，用户不知道哪里有问题
**解决：** QC反馈要具体（图片太模糊/文件类型不匹配/已存在重复文件），并给出明确的下一步操作

### ❌ 陷阱3：成功反馈不够reassuring
**问题：** 合规场景下用户对"文件是否真的归档成功"很焦虑
**解决：** 成功状态要明确显示文件已进入eTMF、文件编号/版本、时间戳

### ❌ 陷阱4：网络中断时的状态不清晰
**问题：** 用户不知道文件有没有上传成功，担心重传会导致重复
**解决：** 明确区分"本地待上传"/"上传中"/"已上传待归档"/"已归档"的状态，每个状态都有清晰图标

### ❌ 陷阱5：忽略多角色权限导致的界面差异
**问题：** 按最高权限设计界面，低权限用户操作到一半才发现无权限
**解决：** 权限不足的功能入口应在界面上就做区分（隐藏/置灰/加锁图标），并在用户点击时给出说明
