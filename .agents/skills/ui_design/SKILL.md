# UI Design

## 角色
UI 设计维护/Reviewer。负责组件与页面的视觉质量，严格遵守 Design System。

## 触发条件
满足以下任一条件时激活：
- 用户要求生成/修改 UI 组件或页面
- 任务涉及 Design Token 使用、样式调整
- 任务涉及设计系统（Design System）维护或更新
- 用户要求审查 UI 视觉质量

**不激活**：纯逻辑/数据层修改（不涉及 UI）；或用户只要求读取/查询代码。

## 执行流程

### 生成/修改 UI 时
1. **上下文确认**：先声明本次引用了哪些 `ui-standards/` 模块，列出给用户确认
2. **Token 检查**：所有色值、间距、圆角、字号必须来自 Design Token，禁止硬编码
3. **图标决策推导**：涉及功能或概念图标时，按【业务与临床图标决策框架】推导图标隐喻、风险分级与呈现形态，禁止随意套用通用图标
4. **状态覆盖**：组件必须覆盖完整交互状态：default / hover / active / disabled / error（适用时含 loading）
5. **自检清单**：遵守 `ui-standards/anti-patterns.md` 的生成前自检清单
6. **交互基准**：遵守 `ui-standards/interaction.md` 的交互基准
7. **输出代码**：生成符合项目规范的组件代码

### Design System 维护
8. **更新 DS 前必须事先通知用户**，说明改动范围和影响
9. **代码 → DS 同步**：如果代码改动影响了设计规范（尤其是 Responsiveness），必须同步更新对应的 `ui-standards/*.md`
10. **DS → 代码同步**：修改 `ui-standards/*.md` 后，检查现有代码是否需要跟进调整，列出影响清单

### 审查模式
11. 审查时只标注问题 + 引用标准，不直接替换设计
12. 检查是否存在「高风险裸图标」、「同形异义歧义图标」、「Emoji 顶替」等反模式
13. 问题分级：`阻断级`（违反硬规则）/ `建议级`（可优化）

## 业务与临床图标决策框架 (Icon Decision Framework)

当界面涉及业务/临床概念或操作图标时，AI 必须基于以下 4 步推理模型推导，而非直接臆造或死记映射：

```mermaid
graph TD
    A[识别业务/临床概念] --> B[Step 1: 实体隐喻推导]
    A --> C[Step 2: 动作与状态解构]
    B & C --> D[Step 3: 风险与呈现分级 (L1-L3)]
    D --> E[Step 4: 歧义拦截与降级判断]
    E --> F[确定最终 Icon 选型与展现形态]
```

### Step 1: 实体隐喻推导 (Entity Metaphor)
- **物理与角色实体**（如 受试者、研究中心、监查员）：采用具象轮廓隐喻（人物、建筑），避免抽象几何图形。
- **数据与输出实体**（如 方案、数据集、CRF、TFL/图表）：依据信息结构特征区分（单页文档 vs 结构化表格 vs 曲线图/森林图），不可统统用单页纸张代表所有数据形态。
- **合规与监管容器**（如 eTMF、归档库、主试验文档）：必须体现“封存/权威归档/容器”属性（带合规标/柜体/合规包），严禁使用普通轻量级临时文件夹隐喻。

### Step 2: 动作与复合状态解构 (Action & Composite State)
- **合规核查与对比**（如 SDV、双人编程核对、质量复核）：采用“双重校验/放大比对/合规印记”隐喻，严禁简化为普通的待办对勾（Checkbox）。
- **不可逆与冻结操作**（如 数据库锁定、归档封印、作废）：采用“强闭锁/印章/熔断”隐喻。
- **复合状态规则**：同一概念在不同生命周期流转时，**保持主体基础图标不变，通过「语义色 + 右下角微角标/Badge」传达状态**（例如：`File` 基础 + `Alert` / `Check` / `Lock` 角标），严禁为每个状态随意发明全新的不相干图标。

### Step 3: 风险与呈现形态分级 (Risk & Presentation Matrix)
依据操作风险与误触成本决定图标的表现形式：

| 风险等级 | 典型场景 | 呈现规则 (Presentation Rule) | 强制约束 |
|---|---|---|---|
| **L3 高风险 / 法规级** | 电子签名 (21 CFR Part 11)、稽查轨迹 (Audit Trail)、数据锁定 (Lock)、严重不良事件 (SAE)、作废 | **强制「图标 + 明确文本标签」** 或提供强提示 Tooltip | ❌ **绝对禁止裸图标（No Naked Icon）**；避免轻浮俏皮线条 |
| **L2 业务流转级** | 临床质疑 (Query)、原始数据核查 (SDV)、版本对比、工作流流转 | **标准隐喻图标 + 状态变体 / 角标计数** | ❌ 严禁脱离临床语境套用普通办公软件图标 |
| **L1 通用工具级** | 搜索、展开/折叠、排序、复制、关闭、分页 | **通用无歧义单图标（Icon-only）**，配备 Accessible Tooltip | ❌ 不在成熟通用工具上过度设计或自创隐喻 |

### Step 4: 业务歧义拦截与优雅降级 (Disambiguation & Fallback)
1. **严禁 Emoji**：任何状态和按钮严禁使用 Emoji 字符顶替功能图标。
2. **同形异义拦截（Collision Check）**：
   - 常见冲突：通用 UI 中的 `?` 代表“帮助中心”，但在数据治理/EDC中代表“数据质疑（Query）”。
   - 规则：在涉及临床业务的上下文中，业务质疑必须采用带标注的消息气泡（如 `MessageSquareQuestion`），将纯问号严格保留给全局系统帮助。
3. **缺失隐喻时的优雅降级（Graceful Degradation）**：
   - 当现有图标库缺失精准隐喻时，**必须主动降级为「纯文本标签」或「上位通用分类图标 + 文本」**，绝不允许为了有图标而强行塞入一个含义模糊、容易引起误导的近似图标。

## 预期输出产物
- **生成模式**：符合 Design System 的组件代码 + 简要说明（引用了哪些 Token、标准及图标推导依据）
- **审查模式**：问题清单（表格：位置 / 问题 / 严重度 / 引用标准）
- **DS 维护**：变更说明 + 影响范围清单

## 验证步骤
- [ ] 所有色值、间距、圆角、字号均来自 Design Token，无硬编码值
- [ ] 图标选型符合【业务与临床图标决策框架】：
  - [ ] L3 高风险/法规级操作无孤立裸图标（必须带文本标签）
  - [ ] 实体与动作隐喻准确，无同形异义认知冲突
  - [ ] 复合状态基于主体图标 + 状态角标/语义色，未随意发明异构图标
  - [ ] 缺失准确隐喻时已优雅降级为文字标签，无 Emoji 顶替
- [ ] 组件覆盖了所有必要的交互状态
- [ ] 如引用了 `ui-standards/` 模块，已在输出中声明
- [ ] 审查模式下，每个问题都引用了对应的标准条款
- [ ] DS 变更已通知用户并列出影响范围
